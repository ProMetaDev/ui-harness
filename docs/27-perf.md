# 性能基线（v0.1.7）

先有尺子，再谈优化。`tools/bench.sh` 测的是**墙钟中位数（5 次）与峰值 RSS**，
不是"感觉快了"。

```bash
bash tools/bench.sh
```

## 冷启动与轻量命令

| 命令 | 中位数 | 峰值 RSS |
|---|---|---|
| `ui --version` | 11 ms | — |
| `ui doctor` | 10 ms | 3.6 MB |
| `ui policy`（单条判定） | 11 ms | — |
| `ui run`（1 步 1 工具，mock） | 29 ms | 3.9 MB |

单二进制、零依赖，启动没有"加载框架"的成本。

## 观测与沙箱的每次开销

2000 个文件的工作区，一条 `shell`：

| 配置 | 中位数 |
|---|---|
| 观测开（默认） | 64 ms |
| 观测关（`UI_OBSERVE=0`） | 54 ms |

**+10 ms / 2000 文件**（两次扫描，约 5 ms 一次）。这是"审计要不要看实际改动"的价格。

`ui lab pack`（2000 文件）：**94 ms**。

## 大日志：从线性内存改成流式

这是这一轮修掉的真问题。

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `verify` 1 万条 | 49 ms / 12.9 MB | 31 ms / 3.6 MB | 内存 -72% |
| `verify` 7 万条 | 256 ms / **80.6 MB** | **162 ms / 3.6 MB** | 内存 **-95%**，时间 -37% |
| `replay --json` 7 万条 | 267 ms / 81.3 MB | **31 ms / 3.0 MB** | 时间 **-88%**，内存 **-96%** |

关键是**内存不再随日志增长**：7 万条 3.6 MB，100 万条也还是 3.6 MB。
优化前是线性的——审计工具在最需要它的场景（大日志）反而先撑不住。

### 怎么做到的

| 命令 | 改动 |
|---|---|
| `verify` | 新增 `ui-core/src/stream_verify.rs`：`BufReader` 逐行读，只保留 `prev`/`seq`/未完成调用集合，每条解析完立即丢弃 |
| `replay` | 逐行解析、逐行打印；`--json` 直接吐原始行（连解析都省了）；事件数用一遍轻量计行得到 |

一致性用 4 个测试钉住（`ui-core/tests/stream_verify.rs`）：干净日志、正文被改、
尾部截断、空日志。**流式路径必须和内存路径给出同样的判定**——换实现最怕的是
"坏日志被判好"。

## 还没优化的地方

| 位置 | 现状 | 为什么先不动 |
|---|---|---|
| `ui export` | 仍把全部事件读进内存 | HTML 要把数据整体嵌进去，O(n) 是固有的 |
| `ui lab pack` 扫描工作区 | 全量遍历 | 2000 文件 94 ms，还能接受 |
| 观测扫描 | 每次 shell 两次全量 stat | 可以按目录 mtime 做增量，但复杂度高、收益待测 |
| 启动后的日志打开 | 会读全量日志（`Journal::open`） | 大日志上启动会慢；目前 7 万条约 100 ms |

最后一条是下一个明显的目标：**`ui run` 在一个 15 MB 的日志上启动要多久**。
如果它明显慢，`Journal::open` 也应该改成"只读尾部 + 校验由 verify 负责"。
