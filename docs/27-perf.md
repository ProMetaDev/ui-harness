# 性能基线（v0.1.7）

先有尺子，再谈优化。`tools/bench.sh` 测的是**墙钟中位数（5 次）与峰值 RSS**，
不是"感觉快了"。

```bash
bash tools/bench.sh
```

## 冷启动与轻量命令

| 命令 | 中位数 | 峰值 RSS |
|---|---|---|
| `ui --version` | 11 ms | — |
| `ui doctor` | 10 ms | 3.6 MB |
| `ui policy`（单条判定） | 11 ms | — |
| `ui run`（1 步 1 工具，mock） | 29 ms | 3.9 MB |

单二进制、零依赖，启动没有"加载框架"的成本。

## 观测与沙箱的每次开销

2000 个文件的工作区，一条 `shell`：

| 配置 | 中位数 |
|---|---|
| 观测开（默认） | 64 ms |
| 观测关（`UI_OBSERVE=0`） | 54 ms |

**+10 ms / 2000 文件**（两次扫描，约 5 ms 一次）。这是"审计要不要看实际改动"的价格。

`ui lab pack`（2000 文件）：**94 ms**。

## 大日志：从线性内存改成流式

这是这一轮修掉的真问题。

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `verify` 1 万条 | 49 ms / 12.9 MB | 31 ms / 3.6 MB | 内存 -72% |
| `verify` 7 万条 | 256 ms / **80.6 MB** | **162 ms / 3.6 MB** | 内存 **-95%**，时间 -37% |
| `replay --json` 7 万条 | 267 ms / 81.3 MB | **31 ms / 3.0 MB** | 时间 **-88%**，内存 **-96%** |

关键是**内存不再随日志增长**：7 万条 3.6 MB，100 万条也还是 3.6 MB。
优化前是线性的——审计工具在最需要它的场景（大日志）反而先撑不住。

### 怎么做到的

| 命令 | 改动 |
|---|---|
| `verify` | 新增 `ui-core/src/stream_verify.rs`：`BufReader` 逐行读，只保留 `prev`/`seq`/未完成调用集合，每条解析完立即丢弃 |
| `replay` | 逐行解析、逐行打印；`--json` 直接吐原始行（连解析都省了）；事件数用一遍轻量计行得到 |

一致性用 4 个测试钉住（`ui-core/tests/stream_verify.rs`）：干净日志、正文被改、
尾部截断、空日志。**流式路径必须和内存路径给出同样的判定**——换实现最怕的是
"坏日志被判好"。

## 还没优化的地方

| 位置 | 现状 | 为什么先不动 |
|---|---|---|
| `ui export` | 仍把全部事件读进内存 | HTML 要把数据整体嵌进去，O(n) 是固有的 |
| `ui lab pack` 扫描工作区 | 全量遍历 | 2000 文件 94 ms，还能接受 |
| 观测扫描 | 每次 shell 两次全量 stat | 可以按目录 mtime 做增量，但复杂度高、收益待测 |
| 启动后的日志打开 | 会读全量日志（`Journal::open`） | 大日志上启动会慢；目前 7 万条约 100 ms |

最后一条是下一个明显的目标：**`ui run` 在一个 15 MB 的日志上启动要多久**。
如果它明显慢，`Journal::open` 也应该改成"只读尾部 + 校验由 verify 负责"。

## 启动路径：open 不再读全量（v0.1.8）

上一节还留着"日志打开会读全量"这一条。现在也修了。

| 场景 | 修前 | 修后 |
|---|---|---|
| `ui run`（7 万条 / 15 MB 日志） | 505 ms / **83.4 MB** | **129 ms / 3.85 MB** |
| `ui run`（空日志，对照） | 33 ms / 3.8 MB | 31 ms / 3.87 MB |

30 万条（62 MB）也测了，内存**不变**：

| 命令 | 时间 | 峰值 RSS |
|---|---|---|
| `ui run`（30 万条） | 229 ms | **3.87 MB** |
| `ui verify`（30 万条） | 664 ms | 3.68 MB |
| `ui replay --json`（30 万条） | 127 ms | 3.23 MB |

### 改了三处

1. **`Journal::open` 只扫尾部**：逐行读但不解析（只在字节里找 `turn/start` 标记），
   只解析最后一条记录拿 `seq`/`prev`；尾部没换行就是撕裂，照旧截断修复。
2. **`catch_up` 只读 offset 之后的内容**：之前每次 append 都 `fs::read` 整个文件——
   15 MB 的日志上每写一条事件就读 15 MB。这是 `open` 改完仍然 18 MB 的真正原因。
3. **`resume` 改为从文件流式取未完成调用**：`open` 不再保留全量事件，
   未完成的调用必须从磁盘读（否则会被 2000 条的内存上限挤掉而漏掉）。

### 语义变化（写在这里，避免误解）

| 变化 | 说明 |
|---|---|
| `open()` 后 `events` 只含最后一条 | 需要全量请用 `Journal::load`（一次性命令）或流式校验 |
| `open()` **不**做全链校验 | 只校验尾部那条自身的 hash；全链校验是 `ui verify` 的职责 |
| 轮次用 `turn_count()` | 不再数 `events`（事件缓冲有上限） |
| 空行不算记录 | 外部工具插空行不会让 seq 归零 |

代价是"追加前不再验证整条链"。**这是有意的取舍**：`verify` 依然是全链校验，
而且现在又快又省内存（30 万条 664 ms / 3.7 MB）；把全链校验放进每次 `run` 的启动路径，
等于让日常操作替审计付钱。

## 观测：从扫描改成事件（v0.1.9）

观测式效果最初是"每个 shell 调用前后各扫一次工作区"。文件一多，这个成本就压不住：
20k 文件的工作区里，**每次 shell 调用要多花 85 ms**。

改成 inotify（Linux，零依赖直接调 syscall）：目录事件驱动，每次调用只 drain 一下队列。

| 工作区 | 关闭观测 | 全量扫描 | **inotify** | 每次开销 |
|---|---|---|---|---|
| 2,000 文件 | 9 ms/次 | 12 ms/次 | **9 ms/次** | 3 ms → **0.5 ms** |
| 20,000 文件 | 38 ms/次 | 123 ms/次 | **43 ms/次** | 85 ms → **5 ms** |

20 次 shell 调用的整轮耗时（20k 文件）：**2474 ms → 864 ms**。

### 两条路径与回退

| 情况 | 行为 |
|---|---|
| Linux，watch 建得起来 | inotify，事件驱动（$`source: "inotify"`$） |
| 平台不支持 / watch 数超限（>4096 目录）/ 事件队列溢出 | 退回全量扫描（$`source: "scan"`$） |
| $`UI_OBSERVE_SCAN=1`$ | 强制扫描（对照组，也是逃生口：overlay/网络文件系统上 inotify 可能不可靠） |
| $`UI_OBSERVE=0`$ | 完全关闭 |

溢出时不假装完整：事件里带 $`overflowed: true`$，说明这次改动可能不完整。

### 一个必须处理的竞态

"建目录"和"往里写文件"几乎同时发生，watch 挂上之前的事件会丢。
所以新建目录时，挂完 watch 还要**把这个子树扫一遍**补记已有文件——
这是竞态修复，不是优化。

另外做了去重：刚创建又写入的文件算"新增"，不再重复算"修改"。

## 校验只读四个字段（v0.1.10）

`ui verify` 需要的是 `seq / prev / kind / callId` 四个字段，但之前每条事件都做完整
JSON 解析——日志里 `prompt/snapshot` 这类事件很大，解析它们纯属浪费。

改成字段级扫描：只对需要的键取值，其余值直接跳过（不分配字符串）。
只有 `tool/start` / `turn/start` 才完整解析（`resume` 要拿 `args`）。

| 场景 | 之前 | 现在 |
|---|---|---|
| `verify` 1 万条 | 31 ms | **22 ms** |
| `verify` 30 万条 / 62 MB | 664 ms | **549 ms** |

内存仍是 3.4 MB，不随日志增长。

**第一次改反而更慢了**（975 ms）：因为对每个未知字段都调了 `read_value`，
扫描整个字符串并分配 `String`。改成"先看键名，未知键直接跳过"才拿到收益。

正确性由同一组测试保证（干净 / 正文被改 / 尾部截断 / 空日志 / 缺失日志），
扫描器遇到任何看不懂的结构（转义、嵌套）都退回完整解析——宁可慢，也不把坏日志判成好的。

## 导出改成流式（v0.1.11）

`ui export` 原来把全部事件读进内存，先拼成一个字符串，再 `replace` 进模板——
峰值是**两份完整数据**。7 万条就要 112 MB，30 万条会到 480 MB。

改成流式：模板切成前缀/后缀，中间边读日志边写文件。

| 场景 | 之前 | 现在 |
|---|---|---|
| `export` 1 万条 | 48 ms / 16.8 MB | **31 ms / 3.3 MB** |
| `export` 7 万条 / 15 MB | 414 ms / **112.5 MB** | **203 ms / 3.5 MB** |

内存 **-97%**，不再随日志增长。

顺带加了一条约束：**不导出损坏的日志**。导出前先流式校验（30 万条约 0.5s），
正文被改就退出 2、不产出文件——导出的轨迹必须可信。
尾部撕裂（崩溃残留）仍然允许导出，并如实标注。
