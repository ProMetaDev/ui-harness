# 隔离副本：怎么把复制开销再降一档

## 先看清楚现在的机制

`ui team --isolate` 给每个子代理复制一份工作区，同时写 `manifest.txt`：

```
<相对路径>	<源文件 SHA-256>
```

用途只有一个，但很关键——**回写时的漂移检测**：

1. 子代理结束时，父子进程比对"副本 vs manifest 哈希"，算出 `changed` 列表；
2. `ui apply` 只处理 `changed` 里的文件，逐个检查父工作区里这个文件的哈希
   是否仍等于 manifest 里的值；不等就是**漂移**（父工作区在子代理跑的时候被改过）。

所以现在**复制时给每个文件算哈希**，是为了"事后能判断哪些文件变了"。

## 实测数据（这是决策依据）

| 项 | 数值 |
|---|---|
| 我们的 SHA-256 | **359 MiB/s**（64 MiB / 0.178 s，纯 Rust 标量） |
| `cp -a` 34 MB | 124 ms |
| `ui team --isolate`（94 MB / 8000 文件 / 3 代理） | **~1040 ms** |
| 推算：3 份副本的哈希 | 3 × 94 MB ÷ 359 MiB/s ≈ 0.27 s（并发，吃掉 3 个核） |
| 推算：3 份副本的复制 I/O | ≈ 0.34 s（并发） |

**结论：复制 I/O 与哈希成本基本相当，各占约 1/4～1/3。** 上一轮把"读两遍"合成一遍，
省掉的是重复读；现在要再降，只有两条路：让哈希更便宜，或者干脆不算。

## 三个方案

### 方案 B：换一个"够用"的快速哈希（推荐）

漂移检测**不需要密码学强度**——它只需要"同一份内容给同一个值、不同内容几乎不给同一个值"。
审计用的 SHA-256 只保留在真正需要的地方（日志链、实验包产物）。

- 实现 xxHash64（流式，约 **3–5 GiB/s**，比现在快 10 倍以上）；
- `manifest.txt` 改记 `xxh:<16 hex>`；
- 其余逻辑不变：仍然是**内容比对**，语义完全不变，只是算法换了。

| 收益 | 风险 |
|---|---|
| 哈希 0.27 s → **约 0.03 s**，3 副本 1040 ms → **约 800 ms** | 64 位碰撞概率 1e-19 量级，且只用于"是否改动"判断，不背审计结论 |
| 语义零变化，测试几乎不用改 | 需要处理旧 manifest（按长度识别：64 hex = sha256，16 hex = xxh） |

### 方案 A：惰性哈希（不算，只记 size+mtime）

复制时只 `stat` 源文件，记 `(size, mtime_ns)`；结束时再 `stat` 副本，**变了才哈希**。

- 省掉全部哈希成本（约 0.27 s），复制路径完全不读内容；
- 但改变语义：**mtime 相同、内容不同**的改动会漏判（`cp -p`、`touch -r`、某些
  restore 工具会保留 mtime）；反过来，mtime 变但内容没变会误判为"改过"。

| 收益 | 风险 |
|---|---|
| 3 副本约 1040 ms → **约 750 ms** | 漏判 = 该合并的改动被静默跳过；这是"审计工具"最不该犯的错 |

我倾向**不单独用 A**：省下来的 0.27 s 不比"漏掉一个改动"更值钱。

### 方案 A+B：先按 mtime 粗筛，再对"可疑"文件算 xxh

- 多数文件 mtime 不变 → 不算哈希；
- mtime 变了的才算（xxh 很快）；
- 判据仍是内容，不是时间——只是**避免了对没变的文件做无用功**。

| 收益 | 风险 |
|---|---|
| 最省，且不牺牲正确性 | 实现最复杂：要同时记源与副本的 stat，并且要证明"mtime 不变 ⇒ 内容不变"这个前提在什么情况下破 |

## 我的建议

**先做 B（半天）**，拿到 25% 左右的确定收益，风险几乎为零；A+B 留作后续，
如果将来真的遇到 GB 级仓库再上。

B 之后如果要继续压，下一个真正的杠杆不是哈希也不是复制，而是
**reflink（FICLONE）**：在 btrfs/xfs 上复制是 O(1)，那时哈希就成了唯一成本，
B 的价值会进一步放大。ext4（当前 WSL 的工作区）不支持，所以本地测不出收益。

## 实现草图（方案 B）

1. `ui-core/src/fasthash.rs`：流式 xxHash64，`new()` / `update()` / `finish()`；
   用官方向量（空串 `ef46db3751d8e999`、`abc` 等）+ 分块一致性钉住。
2. `manifest.txt` 写成 `<rel>\txxh:<hex>`；读的时候按长度判断新旧。
3. `copy_tree` 里把 `ui_core::sha256::Sha256` 换成 `fasthash::Xxh64`。
4. `read_manifest` / `cmd_apply` 的漂移比较改走同一个函数。
5. 测试：
   - 复制后 manifest 与源文件一致（同文件 → 同值）；
   - 内容改一个字节 → 值变；
   - `--isolate` 全流程 + `apply` 冲突/漂移两个闸仍然工作（现有 `verify_team` / `verify_accept` 覆盖）；
   - 旧 manifest（64 hex）仍能被读出并参与比较。
6. 基准：`tools/bench_observe.sh` 旁边加一个 `tools/bench_isolate.sh`，
   对 94 MB / 8000 文件跑 3 副本，记录中位数。

## 需要你确认的一点

方案 B 会让 `manifest.txt` 里的哈希从 SHA-256 变成 xxHash64。`manifest.txt` 目前**只在本机
临时目录里**（`.ui/agents/<id>/manifest.txt`），不进实验包、不进审计日志——所以**不影响任何
对外可验证的声明**。确认这一点之后我就动手。

## 实现与结果（v0.1.13）

按方案 B 做了，另外顺手补掉一个**真 bug**。

### 做了什么

1. `ui-core/src/fasthash.rs`：流式 xxHash64，用 4 条官方向量 + 分块一致性钉住。
2. `manifest.txt` 改记 `<rel>\txxh:<16 hex>`；旧格式（64 位 SHA-256）仍能读，
   读到时按 sha256 比较，不会误判。
3. `ui-core/src/isolate.rs`：把"找出副本里被改动的文件"从 CLI 挪进核心库，
   **判据从"逐字节比较副本与父工作区"改成"副本内容哈希 vs manifest"**。

### 顺手修掉的盲区

旧实现为了省时间，对 **> 2 MB 的文件直接当成"没改"**：

```rust
let too_big = meta.map(|m| m.len() > MAX_COMPARE_BYTES).unwrap_or(false);
let same = if too_big { true } else { /* 逐字节比较 */ };
```

这意味着子代理改了一个大数据集或模型权重，**改动会被静默丢弃**，而日志里写着
"没有改动任何文件"。现在改成内容哈希，没有大小限制。

回归测试 `isolate::tests::a_change_in_a_big_file_is_detected` 在旧代码上必然失败。

### 数据

同一台机器、同一个 94 MB / 8000 文件的工作区、3 个隔离子代理，各 5 次取中位数：

| 版本 | 中位数 | 各次 |
|---|---|---|
| 基准（SHA-256 + 逐字节比较） | **1014 ms** | 1067 / 1026 / 989 / 1009 / 1014 |
| 现在（xxHash64 + 哈希比对） | **809 ms** | 764 / 840 / 810 / 809 / 802 |

**-20%**（省 205 ms）。两份二进制 sha256 不同、commit 不同，确认是比较两个真实版本。

基准脚本：`bash tools/bench_isolate.sh <基准二进制>`（`tools/bench_isolate.py` 计时）。

### 计时踩的坑

WSL2 的墙钟会被 Hyper-V 时间同步校正，偶发**向后跳**，用 `date` 算差值会出现
**负耗时**（真实见到 -835 ms）。基准改用 Python 的 `time.monotonic()`。

### 仍然存在的缺口（如实记录）

1. **删除不会被合并**：子代理删掉文件，`changed` 里不会出现，父工作区该文件保留。
2. `verify_team.sh` **没有任何断言**，只打印输出——它在门禁里"通过"并不证明协作模式正确。
   真正的行为断言在 `ui-core` 的单元测试和 `verify_accept` 里。
