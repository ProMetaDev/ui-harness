## 一、主流玩家在拼什么

| 工具 | 分数（Terminal-Bench 2.1） | 许可证 | 它最强的地方 | 它的软肋 |
|---|---|---|---|---|
| **Codex CLI** | **83.4%**（GPT-5.5） | Apache-2.0 | 云任务 + GitHub 自动评审（`@codex review`），Rust | 强在"跑"，弱在"事后解释"；API 模式掉云功能 |
| **Claude Code** | 78.9%（Opus 4.8） | 闭源 | 多文件实现最稳；opusplan（规划用大模型、执行用小模型） | 闭源、最贵、只有订阅制 |
| **Gemini CLI** | 70.7% | Apache-2.0 | 每天 1000 次免费、1M 上下文 | 免费额度 2026-06-18 起迁去 Antigravity CLI |
| **OpenCode** | 模型而定 | MIT | 172K stars，75+ provider | 只是壳，质量取决于接的模型 |
| **Cline / Goose** | 模型而定 | Apache-2.0 | Goose 是 MCP 原生（70+ 扩展）、Rust | 生态强、内核薄（策略/审计靠宿主） |
| **Aider** | 模型而定 | Apache-2.0 | git 原生、自动 commit | 迭代变慢 |
| **Hermes**（Nous Research） | — | MIT | **自我改进闭环**：从经验长技能、跨会话记忆、FTS5 会话检索、消息网关（TG/Discord/Slack）、6 种终端后端、cron | 黑箱式学习难审计；工具多但缺少"效果—决策—结果"的强约束 |

**共同点**：现在大家都 MCP + GitHub 集成，能力趋同。真正的差别在**默认姿态**——
Claude Code 偏自主实现，Codex 偏评审与 CI，Hermes 偏"长期陪你"。

**它们共同的空白**（也是我们该占的位置）：

1. **事后说不清**：没有一个把"每一步为什么这么决定"做成可校验的账本。
2. **边界靠提示词或宿主**：策略、审批、沙箱大多不是内核级强制。
3. **成本不可拆**：没人能告诉你"这 5 万 token 花在哪个分段的哪一步"。
4. **绑定重**：要么闭源、要么 40+ 工具 + 一堆运行时依赖。

## 三、我们的位置：审计级、可嵌入的 agent 内核

不跟它们比模型智商（那是模型的活），比三件它们没做的事：

1. **可审计**：任何一次执行，事后能逐条回答"谁、什么效果、谁批准、结果如何"，
   而且日志**可校验**（哈希链）——被改过一个字节就能验出来。
2. **可嵌入**：一个二进制 + 一个 HTML，能塞进别人的产品里，不需要 Node 运行时。
3. **边界是硬的**：策略、审批、路径、进程树、并发写，全是内核强制，不靠提示词。

一句话：**别人卖"更聪明的 agent"，我们卖"你敢让它碰生产的 agent"**。

## 四、要补的三块（按投入产出排序）

| 优先级 | 缺口 | 为什么必须补 | 成本 |
|---|---|---|---|
| P0 | **MCP 客户端**（能接 MCP server 的工具） | 这已是行业底线；不接就等于没有生态 | 中：一个 stdio JSON-RPC 客户端 + 工具注册 |
| P0 | **工具面到 10+**（真正则 grep、patch、todo、job 控制） | 6 个工具在真实仓库里会卡住（实测过：搜索失败导致多烧 3 倍 token） | 中 |
| P1 | **成本杠杆**：前缀缓存命中率 | 85% 输入是重发前缀，命中率是唯一量级级杠杆 | 小：适配器记录 `prompt_cache_hit_tokens` |
| P1 | **可分享的"证据包"** | 审计卖点需要一个交付物：一个能验签的 trace 包 | 小：`ui export --bundle`（日志+快照+校验清单） |
| P2 | **从失败中长技能**（对标 Hermes） | 但要做成**可审计**的：技能是从哪次失败、哪条日志长出来的 | 大 |

## 五、多模式：化解"自主 vs 审计"的矛盾

竞品的优势互相冲突（Claude Code 要"别烦我"，审计要"让我看见"）。解法不是二选一，是**模式**：
同一套内核，不同的默认打扰程度。

| 模式 | 行为 | 适合 |
|---|---|---|
| `quiet` | 能自决的都自决；只有策略明确 `deny` 的动作会被拦 | 熟悉的仓库、批量小改 |
| `standard` | 写文件放行、执行命令要问（默认） | 日常 |
| `strict` | 写入与执行都要问，只有读取放行 | 生产仓库、陌生代码 |

**关键约束（也是壁垒）**：模式只调整**决策严格度**，不改变日志、账本、效果声明的格式。
`deny` 是硬边界，任何模式都不能把它变成允许。

于是有了别人做不到的能力——**事后重判**：

```bash
ui run ... --mode quiet        # 当时没打扰你
ui audit --as strict           # 事后：如果当时是严格模式，哪些动作会被拦下？
```

```
动作 3 个 · 按 strict 重判
1 个动作会被收紧（当时放行、这个模式下要问你），0 个会被放宽：
  seq 9  fs_write  fs.write /tmp/ui-mode/out.txt  allow → ask
```

为什么别人做不到：他们的日志里只有"执行了什么"，没有"这一步的效果集、依据哪条规则、
谁批准的"。我们的 `tool/request` 事件里三样都有，所以能离线重跑策略。

这就是"一站式"的正确形态：**能力上用一个入口覆盖（quiet 时和别人一样顺手），
保证上用同一份日志兜底（要审计时随时重判）。**

## 六、验证方式（不靠嘴）

- 同一任务，我们 vs Claude Code / Hermes，比**事后可解释性**：给定最终 diff，
  谁能逐条说清每一步的依据、批准与代价。
- 红队测试：提示注入让它读 `/etc/passwd`、改 `.git/config`、写工作区外——
  我们的策略与真实路径检查必须全部拒绝并留痕。
- 成本对照：同一任务跑 3 次取中位数（`tools/eval.sh`），比较 token 与步数。
