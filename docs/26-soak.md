# 浸泡测试：长任务可靠性有没有数据支撑

"能连续跑很久"是这套东西的核心卖点之一，但在此之前**我们一次都没测过**。
`tools/soak.sh` 把它变成可复现的两个轴：

```bash
bash tools/soak.sh                        # A:800 步 + B:10 分钟
bash tools/soak.sh --steps 1200 --minutes 20
bash tools/soak.sh --steps 1200 --minutes 0   # 只跑 A
```

| 轴 | 测什么 | 暴露的是什么问题 |
|---|---|---|
| **A. 单进程长任务** | 一个 `run` 里几千次工具调用 | 内存无上限、上下文压缩失效、预算/步数上限 |
| **B. 跨进程连续追加** | 反复跑同一个会话 | 哈希链、会话历史、日志增长、并发锁 |

---

## 第一次跑（2026-11-17，v0.1.4）

`--steps 1200 --minutes 20`

### A：1200 步 / 2376 次工具调用 / 4.96M tokens / 37 秒

| 指标 | 值 |
|---|---|
| 退出码 | 0 |
| 事件数 | 10,712 |
| 压缩次数 | 4 |
| 起始 RSS | 6,292 kB |
| 峰值 RSS | 31,880 kB |
| **内存增长比** | **5.07x** ← 判定失败 |
| 链校验 | PASS |

**结论：`Journal` 把每一条事件都留在内存里。**
10,712 条事件 × JSON 结构 ≈ 25 MB。这不是泄漏，是**无上限增长**：
跑几小时的 agent 会把内存吃光，最后被 OOM 杀掉——而"长任务"恰恰要跑几小时。

### B：20 分钟 / 2653 轮 / 68,978 行 / 25 MB

| 指标 | 值 |
|---|---|
| 轮数 | 2,653 |
| 失败轮数 | **0** |
| 日志行数 | 68,978 |
| 日志大小 | 25 MB |
| 每分钟轮数 | 132.7 |
| 链校验 | PASS |
| 最后一次快照 | 1,807 tok（没有随轮数膨胀） |
| 孤儿进程 | 0 |

**结论：跨进程连续追加是稳的。** 2653 轮零失败，链完整，会话历史被压缩住了
（每轮快照稳定在 1.8k tok，不随轮数线性增长）。

---

## 找到并修掉的两个真问题

### 1. `Journal.events` 无上限（真问题）

```rust
// 修法：内存里只留最近 2000 条，轮次用独立计数，磁盘一条不少
const MAX_KEPT_EVENTS: usize = 2000;
```

- 内存：**5.07x → 2.49x**（峰值 31.9 MB → 15.3 MB）
- 磁盘：事件数仍是 10,712，链完整
- 轮次：改用 `Journal::turn_count()`，不再靠数 `events`

回归测试：`memory_buffer_is_capped_but_disk_keeps_everything`
（断言缓冲有顶、`dropped_events()` 准确、`turn_count()` 正确、磁盘事件一条不少）。

### 2. 没有 `--max-steps`（缺口）

`max_steps` 默认 24——对"跑一小时"远远不够，但之前**没有任何命令行参数能调**。
A 轴第一次跑直接以 `step_budget` 结束，就是这个原因。现在：

```bash
ui run --max-steps 2400 ...
```

它进了 `Limits`，也进了 `Limits::from_json`（`maxSteps`）。

## 这个工具本身也是门禁的一部分吗

不是——浸泡要几分钟到几小时，不适合放进 40 项门禁。
它的定位是**发布前的体检**：每次动内核（journal / budget / compact / agent 循环）后跑一次。

已知没覆盖的：

| 没测 | 原因 |
|---|---|
| 真模型下的长任务 | 要花钱，且模型本身的抖动会掩盖内核问题 |
| Windows 上的浸泡 | 交叉编译能跑，但 `soak.sh` 是 bash；需要单独写 PowerShell 版 |
| 多进程同时写同一份日志 20 分钟 | 门禁里的 3 进程并发只跑几百毫秒 |
| 磁盘写满 / 只读文件系统 | 需要构造环境 |

最后一条值得单独做——**日志写不进去时 agent 应该立刻失败**，而不是继续跑到内存里。目前没测过。
